# Добавление роутера: мастер из четырёх шагов

Кнопка «Добавить роутер» на странице «Роутеры» открывает `/routers/new`.

## Шаг 1. Имя и владелец

Создаётся запись роутера. Продукт и версия пока неизвестны — их определит
RoutX при первой привязке. Ничего не переустанавливается.

Пока роутер не привязался, он не показывается в основной вкладке «Активные»:
он находится во вкладке «Ожидают» на странице «Роутеры». После выхода агента
на связь роутер автоматически переходит в «Активные».

## Шаг 2. Подключение

Автоматически выпускается одноразовый токен привязки и показывается:

* команда `ssh root@192.168.1.1` (IP подставляется пользователем);
* готовая команда установки агента;
* время жизни токена (5 минут).

Страница опрашивает `GET /api/v1/routers/{id}` каждые 3 секунды и сама
переходит на шаг 3, когда роутер становится `online`. Если токен истёк, можно
выпустить новый командой «Выпустить новую команду».

## Шаг 3. Подписка и шаблон

Оба поля необязательны:

* ссылка на подписку `http(s)://…`;
* шаблон из списка.

На этом же шаге есть кнопка **«Включить автостарт»**. Она вызывает
`POST /api/v1/routers/{id}/service` с `action=enable`. Агент включает автозапуск
продукта:

```text
prokop enable   (или forkop enable)
```

Отдельный `/etc/init.d/sing-box` намеренно не включается. Prokop и Forkop сами
запускают sing-box и при каждом старте отключают его standalone-автозапуск:

```text
Disabling standalone sing-box autostart
```

Это штатное поведение продукта, а не ошибка. После перезагрузки `S99prokop`
поднимает Prokop/Forkop, а тот запускает sing-box. При выключении автостарта
агент выключает продукт и, если есть, отдельный init-скрипт sing-box. Это не
запускает и не останавливает службы немедленно — меняется только поведение
после перезагрузки.

Если шаблон выбран, по умолчанию включено «Применить шаблон сразу после
проверки». Тогда мастер:

1. сохраняет подписку (job `connections_apply`);
2. назначает шаблон;
3. строит diff;
4. подтверждает применение (создаётся снимок, при ошибке — откат).

## Шаг 4. Проверка

Мастер выполняет:

1. ожидание задачи подписки;
2. diff/apply шаблона (если выбран);
3. проверку заблокированного сайта через активный прокси;
4. быструю диагностику.

Проверка сайта:

```http
POST /api/v1/routers/{id}/access-check
{ "target": "https://www.youtube.com/generate_204" }
```

Агент (`jn_monitor.uc`) вызывает `clash_api get_proxies`, находит группу
`<section>-out`, берёт активный прокси и выполняет
`clash_api get_proxy_latency <tag> 5000 <target>`. Наружу возвращаются только
задержка, тег и группа — без секретов.

Диагностика:

```http
POST /api/v1/diagnostics
{ "router_ids": ["<id>"], "kind": "quick" }
GET /api/v1/diagnostics/{report_id}
```

На экране показываются количество проверок, предупреждения и ошибки, а также
ссылка на полный отчёт.

## Ошибки

* Подписка не применилась — шаг помечается ошибкой, но проверки сайта и
  диагностика всё равно запускаются.
* Шаблон не применился — показывается сообщение, роутер остаётся привязанным.
* Нет группы прокси — проверка сайта вернёт `no_proxy_group`.
* Clash API недоступен — `clash_api_unavailable`.

Роутер после мастера уже создан и привязан. Его можно открыть кнопкой
«Открыть роутер» и продолжить настройку вручную.

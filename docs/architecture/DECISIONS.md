## 1. Зафиксировано требованиями (🔒)

| Требование | Следствие для реализации |
|---|---|
| Роутер инициирует только исходящий TLS | Нет входящих портов, SSH, проброса портов. Агент — клиент long-poll. |
| Один управляемый продукт на роутер | Обнаружены Forkop и Prokop одновременно → `product_conflict`, все mutate блокируются, read-only разрешён. |
| Запрещено переустанавливать/сбрасывать/заменять продукт | Агент не вызывает установщики, uninstall, reset, миграцию Forkop→Prokop. |
| Только проверенные поверхности | CLI продукта + UCI по allowlist. Прямые правки `sing-box/config.json` и внутренних `.uc` запрещены. |
| Асинхронные задания, состояние переживает рестарт | Очередь в БД, ровно 6 статусов: `queued/running/success/failed/cancelled/timeout`. |
| Регистрация только по инвайтам | 32 символа CSPRNG, TTL 5 мин, одноразово, в БД только SHA-256, атомарное погашение. |
| Шаблон = полный набор + явные исключения | `managed ∪ excluded` покрывает универсум без пересечений; VLESS/Sub-подключения не перезаписываются. |
| Бэкап до применения, откат при безопасной возможности | `backup_ok=true` — обязательное условие перехода apply в `running`. |
| Мониторинг 60 с, разнос, без наложений; здоровье прокси ≠ доступность роутера | Планировщик с детерминированным jitter и per-router lease; отдельные поля `reachable` и `proxy_health`. |
| Диагностика native, отчёты masked, честные GAP | `support_report` не вызывается; недоступное помечается `not_available`, а не имитируется. |
| Версии sing-box из официального источника, проверки, откат, стадии | Только Prokop `core_releases`/`install_version`; Forkop — GAP по версиям. |
| Роли superadmin/user, аудит без секретов, нет произвольного shell | RBAC + owner-фильтр, allowlist операций агента, санитайзер логов. |
| Интерфейс и документация на русском | UI, ошибки, runbook'и, отчёты — на русском. |

### D-01. Серверный стек ✅

**Вопрос:** на каком стеке писать сервер?

**Принято:** Node.js 24 LTS + TypeScript, один процесс. HTTP — Fastify 5, валидация — Zod, ORM/миграции — Drizzle + SQL, логи — Pino. Воркеры заданий работают в том же процессе; при росте нагрузки выносятся в отдельный процесс без смены модели.

**Почему так:** из не-Go вариантов это самый лёгкий по числу компонентов: один рантайм, один процесс, один язык на сервере и фронтенде, без Redis. Ориентир потребления — 100–150 МБ RSS при 100 роутерах (100 long-poll соединений и ~1,7 монитор-задания/с).

**Отклонено:**

* Go 1.23+ — по требованию пользователя (не Go), хотя был рекомендован ранее.
* Node + BullMQ + Redis — лишний брокер; очередь заменена таблицей `jobs`.
* Python 3.12 + FastAPI + arq — второй рантайм для фронтенда, выше расход памяти и сложнее деплой.

**Последствия:** сервер зависит от Node 24; Argon2id выполняется в libuv threadpool (нужен `@node-rs/argon2`, не блокирует event loop); тяжёлые CPU-задачи, если появятся, выносятся в `worker_threads` или отдельный процесс.

### D-02. БД и очередь ✅

**Вопрос:** где хранить состояние и очередь заданий?

**Принято:** PostgreSQL 16; очередь — таблица `jobs` с `FOR UPDATE SKIP LOCKED`; `jsonb` для diff/отчётов; партиционирование метрик по месяцам; `lease_expires_at` для восстановления после падения воркера. Redis не используется.

**Отклонено:**

* PostgreSQL + Redis/BullMQ — быстрее при > ~2000 заданий/мин, но добавляет компонент, который надо бэкапить и мониторить.
* SQLite — проще для одного узла, но нет `SKIP LOCKED`, слабее конкурентная запись и партиционирование; допустим только как dev-режим.

**Последствия:** очередь требует аккуратного reaper'а (`JOBS.md` §3); при росте нагрузки Redis добавляется без изменения модели заданий.

### D-03. Web UI и API ✅

**Вопрос:** SPA или серверный рендеринг; REST или GraphQL?

**Принято:** React 19 + TypeScript (Vite), сборка встраивается в серверный артефакт; REST + OpenAPI 3.1 (схемы Fastify/Zod). Причины: diff-вьюер, графики, таблицы и подтверждения лучше живут в SPA; OpenAPI даёт генерацию клиента и контрактные тесты.

**Отклонено:** SSR + HTMX + шаблоны (сложнее интерактивный diff и массовые подтверждения); GraphQL (лишний слой для CRUD-панели).

**Последствия:** этап сборки фронтенда в CI; статические ассеты встраиваются в артефакт, без CDN.

### D-04. Протокол «сервер ↔ агент» ✅

**Вопрос:** как доставлять команды на роутер без входящих портов?

**Принято:** HTTPS long-poll: `POST /agent/v1/poll`, удержание ≤ 25 с, один командный ответ, bearer-токен роутера + `X-RC-Timestamp`/`X-RC-Nonce`. Причины: работает на `curl`/ucode без новых зависимостей; пока агент держит запрос, команда доставляется почти мгновенно; устойчиво к NAT и перезагрузкам.

**Отклонено:** WebSocket (сложнее на ucode/curl, нужен keepalive и прокси-совместимость); MQTT (отдельный брокер и клиент, больше точек отказа).

**Последствия:** задержка доставки при простое ≤ 25 с; при 1000+ роутерах нужен пул соединений и лимиты (этап 10).

### D-05. Деплой сервера ⚪

**Принято по умолчанию:** Docker Compose (app + PostgreSQL 16 + Caddy) как основной сценарий; systemd-юнит + внешний PostgreSQL — документированная альтернатива. Оба варианта в runbook. Kubernetes в v1 не поддерживается.

**Последствия:** healthcheck'и, volume для БД, `.env` для `RC_MASTER_KEY`; обновление — с бэкапом и миграциями expand/contract.

### D-06. Платформы и варианты sing-box ✅

**Вопрос:** какие OpenWrt/архитектуры/варианты sing-box считаем поддерживаемыми?

**Принято:**

| Параметр | Поддерживается | Вне поддержки (read-only) |
|---|---|---|
| OpenWrt | 24.10.x (opkg) и 25.12+ (apk) | 23.05 и ниже, прочие сборки |
| Архитектура | `aarch64_cortex-a53` (Filogic), `aarch64_generic` (Rockchip) | остальные |
| Forkop | вариант sing-box (`stable/tiny/extended/extended_compressed`) | выбор версии — GAP |
| Prokop | вариант + версия `extended` из `core_releases` | версии для `stable/tiny` |

Обоснование: аудит подтверждает у Prokop ветки `24.10.*` (opkg) и `25.12+` (apk), у Forkop — `≥ 24.10` и apk для новых; зеркала Prokop — только две архитектуры. Путь apk проверен по коду установщиков, но требует живого теста на этапе 3; до него 25.12+ помечается `supported` с флагом `apk_untested` и не участвует в staged rollout.

Неподдерживаемая платформа не блокирует мониторинг и диагностику, но блокирует apply и установку компонентов.

**Отклонено:** 23.05 (нет проверки upstream); все архитектуры best-effort (противоречит принципу «отказ безопаснее догадки»); только 24.10 (сужает парк без причины).

### D-07. Политика 2FA ✅

**Вопрос:** кто обязан использовать TOTP?

**Принято:** политика по умолчанию — `all`: TOTP обязателен для всех пользователей, включая первого superadmin (enrollment при первом входе, до него доступен только экран настройки 2FA). Допустимые значения политики — `all` и `admins`; `off` отсутствует. Ослабление до `admins` — только superadmin, через step-up и с записью в аудит. Recovery-коды — 10 одноразовых.

**Отклонено:** `admins` по умолчанию (слабее для обычных пользователей); `off` (снимает защиту привилегированного аккаунта).

**Последствия:** поле `settings.twofa_policy`; приглашённый пользователь не может войти без enrollment; сброс 2FA — только superadmin, с уведомлением в аудит.

### D-08. Лимиты ✅

**Вопрос:** какие лимиты ставим по умолчанию?

**Принято:**

| Лимит | Значение |
|---|---|
| Роутеров на инстанс | 100 |
| Учётных записей на сервере (включая открытые приглашения) | 20 |
| Роутеров на пользователя | 10 |
| Роутеров в batch | 10 |
| Шаблонов на пользователя | 50 |
| Одновременных full-диагностик | 3 на инстанс, 10/час на роутер |
| Poll агента | 10/мин на роутер (long-poll не считается) |
| Создание заданий | 60/мин на пользователя |

Все значения — в `settings`, меняются суперадмином; при превышении — `validation_failed`/`rate_limited`, без тихого усечения. Batch не может превышать лимит роутеров на пользователя.

**Отклонено:** 20/50/500 (избыточно для выбранного масштаба); 50/200/2000 (провайдерский сценарий, потребовал бы Redis и шардирования).

**Последствия:** 100 роутеров при 60-секундном мониторинге ≈ 1,7 задания/с — один процесс Node справляется; при подходе к лимиту — вертикальное масштабирование или отдельный worker-процесс, без смены схемы.

### D-09. Пороги мониторинга ✅

**Вопрос:** когда считать роутер offline, а прокси деградировавшим?

**Принято:**

* Цель — 60 с, jitter 0…15 с, один in-flight на роутер.
* `router_offline` — 3 подряд неуспешных poll'а (≈ 3 мин); далее интервал удваивается до 5 мин, возврат к 60 с после 3 успехов.
* `proxy_unhealthy` — latency не измерена или `check_proxy != 0`.
* `proxy_degraded` — p95 за 5 минут > 1500 мс **или** ≥ 1 мёртвый тег в активной группе.
* `service_down` — роутер отвечает, `running=0` и `stopped_by_user != 1` (Prokop) / нет `running` (Forkop).
* Здоровье прокси никогда не выводится из доступности роутера и наоборот.

**Отклонено:** 2 пропуска / 2 мин (агрессивнее, больше ложных тревог при мобильном интернете); 5 пропусков / 5 мин (спокойнее, но позже реакция); порог 2000 мс (пропускает деградацию).

**Последствия:** пороги — настройки инстанса; смена порога пересчитывает только будущие точки, историю не переписывает.

### D-10. Retention ✅

**Принято:** не более 30 дней для метрик, отчётов, заданий и аудита; короче — можно, длиннее в v1 — нет.

| Данные | Срок |
|---|---|
| Сырые точки мониторинга | 30 дней (drop партиций) |
| Часовые агрегаты | 30 дней |
| Суточные агрегаты | не используются в v1 (схема сохранена) |
| Отчёты диагностики | 30 дней |
| Задания (все статусы) | 30 дней |
| Команды агента | 7 дней после ack |
| Аудит | 30 дней |
| Сессии | 30 дней неактивности |
| Инвайты/привязки | 30 дней после истечения |
| Снапшоты | Prokop — upstream; локальные — 10 на роутер |
| Каталог версий sing-box | 30 дней |

**Компромисс:** 30 дней аудита — короткое окно для разбора инцидентов; выбран пользователем осознанно. Если позже потребуется 90/180 дней, меняется только retention-политика и размер партиций, схема не переделывается.

**Последствия:** retention-джоба ежедневно; удаление аудита — только ею, пачками, с записью в служебный лог (не в сам аудит). Партиции метрик создаются на 2 месяца вперёд.

### D-11. Бэкап и DR сервера ✅

**Вопрос:** как защищаем состояние сервера?

**Принято:**

* Ночной `pg_dump -Fc`, шифрование `age`, выгрузка в S3-совместимое хранилище вне сервера.
* Хранение: 14 дневных, 8 недельных, 12 месячных.
* RPO 24 ч, RTO 1 ч (поднять Compose + восстановить дамп + прогнать миграции).
* `RC_MASTER_KEY` — отдельно от дампа, в офлайн-хранилище; потеря ключа = повторный enrollment 2FA (данные не восстановимы).
* Квартальная учебная реставрация на чистом стенде.
* PITR (WAL-G) — опция этапа 10, не обязательство v1.

**Отклонено:** только локальные дампы (не переживает потерю VPS); PITR с первого дня (RPO ≈ 5 мин, но +хранилище и +эксплуатация).

**Последствия:** runbook `backup-restore`; проверка восстановления входит в критерий приёмки этапа 1.

### D-12. Self-update агента ✅

**Вопрос:** может ли сервер обновлять агент на роутере?

**Принято:** нет. Агент обновляется только вручную: подписанный `.ipk`/`.apk` + SHA-256 из релиз-манифеста, установка через пакетный менеджер. Сервер показывает `agent_version`, доступную версию и статус `agent_version_unsupported`, но не имеет операции «обнови себя».

**Отклонено:** push подписанного пакета (нужны ключи, откат, проверка совместимости); автообновление из репозитория (риск сломать парк без предупреждения).

**Последствия:** при критической уязвимости агента — ручная кампания по парку; сервер помогает списком отстающих.

### D-13. Права на sing-box ✅

**Вопрос:** кто может устанавливать версии sing-box?

**Принято:** пользователь может устанавливать версии sing-box **на свои** роутеры. Условия:

* только тег из проверенного каталога `core_releases` (Prokop) и только вариант `extended`;
* обязательный снапшот конфигурации до установки и post-check после;
* явное подтверждение с показом текущей и целевой версии;
* 1 установка на роутер в 24 часа, чтобы не устраивать циклы;
* staged rollout и смена стадий — только superadmin;
* чужой роутер → `404`.

Superadmin может устанавливать на любой роутер и управлять rollout.

**Отклонено:** только superadmin (ограничивало бы владельцев роутеров); делегирование флагом (избыточно на 20 пользователей).

**Последствия:** сервер проверяет owner + роль на каждом запросе, не только в UI; откат версии — новая установка предыдущего тега, не «отмена».

| Продукт | OpenWrt | Архитектуры | Версии sing-box | Статус |

«Поддержка» означает: агент ставится и работает поверх **уже установленного** продукта. Установку, миграцию и удаление продуктов RoutX не выполняет.

## 4. Лимиты и таймауты (итог D-08)

См. таблицу D-08. Дополнительно:

* тело Web API — 1 МБ; результат агента — 256 КБ; отчёт (gzip) — 2 МБ;
* `apply_uci.ops` ≤ 200; `proxy_latencies.tags` ≤ 250; `logs_tail.lines` ≤ 200;
* TTL mutate-команды — 10 мин, read — 2 мин;
* backoff агента 5 с → 5 мин, jitter ±20 %; при 401 — стоп и `re_bind_required`;
* batch apply — последовательный, не более 10 роутеров.

## 5. Пороги и классификация (итог D-09)

```text
router_offline   = 3 пропуска poll подряд
service_down     = reachable && running=0 && !stopped_by_user
proxy_unhealthy  = delay отсутствует || check_proxy != 0
proxy_degraded   = p95(5m) > 1500 ms || dead_tags >= 1 в активной группе
unknown          = нет данных (старый агент / GAP)
```

`reachable` и `proxy_health` — независимые поля; в UI две отдельные колонки и две отдельные тревоги.

## 7. Вне области v1

* Установка/переустановка/удаление/сброс Forkop и Prokop, миграция между ними.
* Серверный (inbound) режим Forkop, Reality-ключи, inbound-секреты.

## 9. Значения по умолчанию (⚪, не блокируют)

1. **Архив роутеров.** Soft-archive: роутер скрыт, токен отозван, история сохранена; жёсткое удаление — только superadmin и только без назначенных шаблонов.
2. **mTLS.** Выключен по умолчанию, включается на этапе 10; bearer + nonce обязательны всегда.
3. **`logs_tail` через `logread`.** Выключен по умолчанию; используются только `check_logs`/`check_sing_box_logs`. Включение — настройка инстанса + аудит.
4. **Auto-reconcile дрейфа.** Выключен; при включении — обычный apply со снапшотом и записью в аудит.
5. **Уведомления.** Только in-app на v1; SMTP/webhook — после этапа 10.
6. **API-токены автоматизации.** Выключены по умолчанию; при включении — только superadmin, scopes не выше прав владельца.
7. **Шифрование локальных снапшотов Forkop.** v1 — права 0600 без шифрования (на роутере нет гарантированного `gpg`/`openssl`); при требовании — отдельный режим с паролем суперадмина.

# RoutX — безопасность

Модель угроз, аутентификация, авторизация, работа с секретами, защита агента и аудит.

---

## 1. Модель угроз (кратко)

| Угроза | Вектор | Мера |
|---|---|---|
| Кража сессии | XSS, украденный cookie | HttpOnly/Secure/SameSite, CSP, короткий TTL, отзыв |
| Подбор пароля | логин-эндпоинт | Argon2id, лимит попыток, lockout, одинаковые ответы |
| Кража инвайта/токена привязки | перехват, утечка логов | TTL 5 мин, одноразовость, только хэш в БД, не логируется |
| Подмена роутера | украденный agent-токен | TLS, ротация, отзыв, nonce/timestamp, аудит |
| MITM | сеть между роутером и сервером | TLS ≥ 1.2, проверка CA, запрет `-k`, опционально pinning SPKI |
| Компрометация роутера | доступ к файлам | токен 0600, снапшоты 0600/0700, отсутствие shell-API |
| Вредоносная команда с сервера | подмена ответа/БД | фиксированный allowlist операций и argv; агент не исполняет строки |
| Утечка секретов в отчётах | `support_report`, `raw` | запрет `support_report`, masked-only, санитайзер |
| Эскалация прав | IDOR | owner-фильтр, opaque ID, 404 вместо 403 |
| Подмена upstream-конфига | env-переменные | `env -i` с фиксированным PATH |
| Supply chain | обновление агента/сервера | подписанные релизы, SHA-256, отсутствие self-update в v1 |
| DoS на сервер | массовые poll/диагностика | rate limit, лимиты размера, per-router сериализация |

Вне области: защита от физического доступа к роутеру и от компрометации самого upstream-продукта (Forkop/Prokop). Если роутер скомпрометирован, он может врать в отчётах — это принимается, но не даёт доступа к другим роутерам.

## 2. Аутентификация пользователей

### 2.1. Пароли

* Argon2id: `m=64 MiB, t=3, p=4` (параметры хранятся в хэше, допускают апгрейд).
* Минимум 12 символов, проверка по списку самых частых (локальный словарь, без внешнего API).
* Смена пароля → отзыв всех сессий, кроме текущей.
* Сброс — только суперадмином (в v1 без e-mail-восстановления) с обязательной сменой при входе.

### 2.2. Сессии

* Opaque 256-бит токен, в БД — SHA-256; сравнение за постоянное время.
* Cookie: `HttpOnly; Secure; SameSite=Lax; Path=/`, без `Domain`.
* TTL 30 дней, скользящее продление при активности, абсолютный максимум 90 дней.
* Смена пароля/2FA/роли → отзыв.

### 2.3. 2FA (TOTP, RFC 6238)

* Секрет 160 бит, base32, шифруется AES-256-GCM перед записью.
* Окно ±1 шаг (30 с), защита от повторного использования кода (последний принятый шаг хранится в `users.totp_last_step`).
* Включение — только после успешного подтверждения кодом.
* Recovery-коды: 10 одноразовых, хэши, показываются один раз.
* Политика (настройка инстанса): `all` (по умолчанию) | `admins`; значения `off` нет. TOTP обязателен для всех, включая первого superadmin (enrollment при первом входе). Ослабление до `admins` — step-up + аудит (см. `DECISIONS.md` D-07).

### 2.4. Инвайты

* 32 символа CSPRNG, алфавит Crockford base32 (160 бит).
* В БД только SHA-256; plaintext показывается один раз.
* TTL 5 минут (настраивается 5–60), одноразовый, атомарное погашение (см. `DATA_MODEL.md`).
* Погашение: rate limit 5/мин на IP + 10/час на токен; неудачи инкрементируют `attempts`.
* Инвайт с ролью `admin` или `superadmin` может создать только суперадмин;
  администратор приглашает только `user` в свою ветку.

## 3. Авторизация (RBAC)

### 3.1. Роли

| Возможность | superadmin | admin | user |
|---|---|---|---|
| Свои роутеры (CRUD, bind, apply) | все | только свои | только свои |
| Чужие роутеры | да (поддержка) | нет | нет |
| Смена продукта, удаление пакетов | да | да, только свои | нет |
| Передача роутера | любой | свой → в свою ветку | нет |
| Шаблоны | все + глобальные | свои + общие | свои + общие |
| Пользователи, инвайты | все | только своя ветка; приглашает только `user` | нет |
| Политика 2FA, лимиты, retention | да | нет | нет |
| Каталог версий sing-box, rollout | да | просмотр (свои роутеры) | просмотр (свои роутеры) |
| Установка sing-box на свой роутер | да (любой роутер) | да (только свои) | да (только свои; каталог `extended`, 1 установка/24 ч) |
| Обновление агента RoutX | все роутеры | свои + роутеры своей ветки | нет |
| Аудит | весь | нет | нет |
| Секреты (показ/ротация) | да | нет | нет |
| Вход под пользователем | да | нет | нет |
| Настройки инстанса | да | нет | нет |

### 3.2. Правила

1. Каждый запрос к объекту содержит `owner_id` в WHERE; чужой объект → `404`.
2. `superadmin` не «обходит» аудит: его действия логируются так же.
3. Опасно-чувствительные операции (передача роутера, ротация токена, отключение 2FA, установка версии sing-box, массовый apply > 5 роутеров) требуют повторного ввода пароля (step-up) и/или TOTP.
4. Пользователь не может повысить себе роль; роль меняет только суперадмин.
   Администратор может управлять только пользователями своей ветки и не может
   назначать роль выше `user`.
5. Удаление пользователя запрещено, пока у него есть роутеры (нужна передача или архивация).
6. API-токены (если включены) имеют scopes и не могут превышать права владельца.
7. Вход под пользователем (`impersonation`) доступен только суперадминистратору.
   Сессия живёт 2 часа, 2FA не запрашивается повторно, но возврат к своей
   учётной записи возможен только при наличии отдельной HttpOnly-cookie с
   исходной сессией суперадминистратора. Старт и завершение пишутся в аудит;
   действия в режиме входа выполняются от имени выбранного пользователя.
8. Обновление из панели выполняет отдельный контейнер `updater` с доступом к
   Docker socket. Панель не получает socket: она может только записать
   `update`/`rollback` в каталог `update/`. Скрипт updater принадлежит root и
   принимает только эти две команды. Это ограничивает последствия компрометации
   панели обновлением или откатом образа, но не даёт произвольный доступ к хосту.

### 3.3. Изоляция через ID

* Наружу отдаются только UUID объектов; внутренние имена секций UCI, e-mail других пользователей, ID заданий других владельцев не раскрываются.
* Ошибки авторизации и «не найдено» неразличимы (`404`).
* Временные ссылки на отчёты — подписанные, TTL 10 мин, привязаны к пользователю.

## 4. Секреты

### 4.1. Классификация

| Секрет | Где хранится | Как защищён |
|---|---|---|
| Пароли пользователей | `users.password_hash` | Argon2id |
| TOTP-секреты | `users.totp_secret_enc` | AES-256-GCM |
| Recovery-коды | `users.recovery_codes` | SHA-256 |
| Сессионные токены | `sessions.token_hash` | SHA-256 |
| Инвайты/привязки | `*.token_hash` | SHA-256 |
| Сброс пароля | `password_resets.token_hash` | SHA-256, одноразовый, 1 час |
| Токены агентов | `router_credentials.token_hash` | SHA-256 |
| Ключ шифрования | env `RC_MASTER_KEY` или файл 0400 вне БД | не в БД, не в логах |
| Секреты шаблонов (VLESS, URL подписки, inbound) | **не покидают роутер** | не читаются агентом |
| Подписки/VLESS, добавленные во вкладке «Подключения» | `router_connections.secret_enc` | AES-256-GCM, в UI только маска |
| Компактные секреты `rc1.…` | `router_connections.compact_secret` | AES-256-GCM, ключ HKDF-SHA256 от `RC_MASTER_KEY`; в API только по явному запросу с аудитом |
| Снапшоты Forkop | роутер, `/etc/routx/snapshots` | 0600/0700 |

### 4.2. Правила

* Секреты шаблонов (VLESS/Sub/inbound) **не** передаются на сервер вообще — ни в diff, ни в отчётах, ни в снапшотах.
* Исключение — явно добавленные пользователем подписки/VLESS: они передаются по TLS, шифруются AES-256-GCM и никогда не возвращаются в открытом виде через API (только маска).
* `read_state` читает только allowlist не секретных опций.
* `support_report` не вызывается.
* `show_config raw` / `show_sing_box_config raw` запрещены в агенте.
* Логи и аудит: allowlist полей; значения секретных опций вырезаются **до** записи.
* Ошибки upstream могут содержать URL/теги — перед сохранением прогоняются через санитайзер (regex на `vless://`, `vmess://`, `ss://`, `trojan://`, `http(s)://…@`, `Bearer`, `token=`).
* Ротация `RC_MASTER_KEY` — процедура с перешифровкой TOTP-секретов и `router_connections`, описана в runbook.

### 4.3. Шифрование в покое

* TOTP-секреты — AES-256-GCM, nonce на запись, AAD = `user_id`.
* Подписки/VLESS — AES-256-GCM (`secret_enc`), в списках API только `masked`.
* Бэкапы БД — шифруются на стороне сервера (age/GPG) перед выгрузкой.
* Диск — LUKS/облачный аналог (рекомендация для продакшена).

## 5. Транспорт и протокол агента

* Только исходящий TLS с роутера; входящих портов нет.
* Проверка сертификата обязательна; `curl --insecure` запрещён в коде агента.
* TLS ≥ 1.2, предпочтительно 1.3; HSTS на сервере.
* Bearer-токен 256 бит, только в заголовке (не в query, чтобы не попасть в access-логи).
* `X-RC-Timestamp` + `X-RC-Nonce`: окно ±300 с, nonce-кэш 10 мин (защита от replay при компрометации логов).
* Ограничение размера тела до чтения (не после): 256 КБ / 2 МБ для отчётов.
* Ответы агента — только JSON по схеме; неизвестные поля игнорируются, но логируются счётчиком.
* При `401` агент **не** ретраит бесконечно: 3 попытки → пауза 5 мин → `re_bind_required` в UI.
* Опционально (этап hardening): mTLS — сертификат выдаётся при bind, приватный ключ генерируется на роутере (если есть `openssl`), иначе серверный; хранится 0600.
* Pinning: при bind сервер отдаёт SPKI-хэш; агент сверяет при каждом соединении (защита от подмены CA на роутере). Отключаемо настройкой, по умолчанию включено.

## 6. Защита агента

1. **Allowlist операций** — закрытый список в коде; сервер не может его расширить.
2. **Никакого shell** — argv-массивы; запрещены `system("…")`, `eval`, подстановки.
3. **`env -i`** — фиксированный `PATH`, никаких унаследованных `PROKOP_*`/`FORKOP_*`/`UCI_*`.
4. **Валидация аргументов** —正则 по типу (action, tag, path, timeout), лимиты длины, запрет `\0`/`\n`.
5. **Один mutate за раз** — локальный lock-файл + проверка upstream-локов.
6. **Идемпотентность** — журнал `command_id` на flash, TTL 7 дней.
7. **TTL команд** — просроченная mutate-команда не выполняется.
8. **Отказ от неизвестного** — `op`, путь, опция, версия манифеста → `capability_missing`.
9. **Файлы** — `/etc/routx` 0700, `agent.conf` 0600, снапшоты 0600.
10. **procd** — `respawn`, но с backoff; при циклическом падении — останов и запись в лог.
11. **Обновление агента** — только через пакетный менеджер / ручную установку; self-update в v1 отсутствует. Пакет публикуется с SHA-256 и подписью релиза.

## 7. Аудит

* События: вход/выход, MFA, инвайты, CRUD пользователей/роутеров/шаблонов, bind/rotate/revoke, diff, confirm, apply, rollback, diagnostics, sb_install, rollout approve, изменения настроек, отказы авторизации.
* Поля: `at, actor_id, actor_role, action, target_type, target_id, router_id, ip, user_agent, result, code, metadata`.
* `metadata` — allowlist на действие. Пример для `apply.confirm`: `{ "apply_run_id", "diff_hash", "items_count", "deletes_count" }` — без значений.
* Аудит append-only: запрещены UPDATE/DELETE (кроме retention-джобы); права БД — только INSERT/SELECT для приложения.
* Retention — 30 дней (`DECISIONS.md` D-10); экспорт доступен в этом окне.
* Экспорт — CSV/JSONL по фильтру, только суперадмин, с записью факта экспорта в аудит.

## 8. Ограничения частоты

| Действие | Лимит |
|---|---|
| Логин | 5 / 15 мин на (email+IP), затем lockout 15 мин |
| MFA-код | 5 / 5 мин |
| Погашение инвайта | 5 / мин на IP |
| Погашение binding-токена | 5 / мин на IP |
| Poll агента | 10 / мин на роутер (long-poll не считается) |
| Создание заданий | 60 / мин на пользователя |
| Диагностика full | 10 / час на роутер |
| Массовый apply | 1 batch одновременно на пользователя |

Реализация: token bucket в памяти + устойчивый счётчик в БД для критичных (логин, инвайты).

## 9. Валидация ввода

* Все ID — UUID; всё остальное — строки с явными ограничениями.
* JSON-схемы для тел запросов (OpenAPI + runtime-валидация).
* Отклонение неизвестных полей (strict mode) для mutate-эндпоинтов.
* Значения UCI валидируются по типу опции (enum/interval/IP/URL/int/bool) **до** `uci set`.
* Запрет на `\0`, `\n`, `\r` в значениях, попадающих в argv.
* Лимиты: имя роутера ≤ 64, имя шаблона ≤ 64, описание ≤ 2 КБ, diff ≤ 200 items, отчёт ≤ 2 МБ.

---

## 10. Логирование и редакция

* Структурные логи (pino JSON), уровни info/warn/error.
* В логи не попадают: тела запросов целиком, заголовок `Authorization`, cookie, токены, значения секретных опций, URL подписок.
* `request_id`/`trace_id` для корреляции; `actor_id`, `router_id` — да.
* Access-лог: метод, путь **без query**, статус, длительность, `router_id` (из токена), без IP в открытом виде (хэш/маска по настройке).
* Ротация и retention логов — 14 дней по умолчанию.

---

## 11. Supply chain и релизы

* Сервер: сборка из закреплённых зависимостей (`package-lock.json`/`pnpm-lock.yaml`), SBOM, подписанные образы (cosign) — рекомендуется.
* Агент: пакет `.ipk`/`.apk` с фиксированной версией, SHA-256 в релиз-манифесте, подпись релиза.
* Никаких внешних CDN для панели (все ассеты в бинарнике) — меньше поверхностей.
* Обновления сервера — только по инструкции с бэкапом БД; миграции — вперёд-совместимые (expand/contract).

---

## 12. Реагирование на инциденты

1. **Утечка токена агента** → отозвать `router_credentials`, выпустить новый binding-токен; роутер в `re_bind_required`; проверить аудит за период.
2. **Компрометация пользователя** → отозвать сессии, сменить пароль, сбросить 2FA (суперадмин), проверить его роутеры на drift, аудит.
3. **Компрометация сервера** → ротировать `RC_MASTER_KEY`, все agent-токены, все сессии; уведомить владельцев; проверить, не отправлялись ли mutate-команды вне обычного поведения.
4. **Подозрительная команда** (необычный шаблон, массовые delete) → `needs_attention`, блокировка apply до разбора, снапшоты сохранены.

---

## 13. Явные ограничения v1

* Нет SSO/OIDC (только локальные аккаунты).
* Нет e-mail-восстановления пароля.
* Нет mTLS по умолчанию (опция hardening).
* Нет self-update агента.
* Подписки/VLESS, добавленные через панель, хранятся на сервере только в AES-256-GCM; секреты шаблонов — по-прежнему нет.
* Нет шифрования снапшотов Forkop на роутере (только права 0600); при требовании — добавить `gpg`/`openssl` и пароль, вводимый суперадмином.

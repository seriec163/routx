# RoutX — архитектура (черновик v1)

Статус: **проект, ожидает согласования открытых решений** (`DECISIONS.md`).
Основано на аудите: `docs/audit/INTEGRATION_MAP.md`.

---

## 1. Цели и принципы

### 1.1. Цель

Централизованно управлять **VPN и прокси на парке роутеров OpenWrt** с установленным **Tachyon, Forkop, Prokop или Podkop**: устанавливать и переключать продукт, хранить шаблоны конфигурации, применять их с подтверждением и откатом, следить за здоровьем, запускать диагностику и управлять версиями sing-box. Самим роутером, его прошивкой и сетью RoutX не управляет.

### 1.2. Не цели v1

* Управление прошивкой OpenWrt, сетью, firewall, DHCP/DNS и другими настройками роутера вне VPN-продукта.
* Управление серверным (inbound) режимом Forkop, Reality-ключами, inbound-секретами.
* Управление killswitch, autotune, уведомлениями, TorrServer, профилями/экспериментами.
* Произвольный shell/SSH на роутере, входящие соединения к роутеру.
* Замена LuCI: панель дополняет, а не переписывает локальный UI.

### 1.3. Принципы

1. **Роутер инициирует всё.** Никаких пробросов портов, SSH, входящих API. Только исходящий HTTPS.
2. **Только санкционированные поверхности.** CLI продукта + UCI по белому списку + чтение файлов состояния. Никаких прямых правок сгенерированного `config.json`.
3. **Два адаптера, один контракт.** Различия Forkop/Prokop инкапсулированы; общий код не знает про `service.prokop`/`service.forkop`.
4. **Всё изменяющее — асинхронно и идемпотентно.** Задание имеет ID, попытки, дедлайн, результат в БД. Рестарт сервера ничего не теряет.
5. **Сначала бэкап, потом изменение.** Нет снапшота — нет apply.
6. **Никаких секретов в логах, аудите и отчётах.** Маскирование на роутере, повторная проверка на сервере.
7. **Честные GAP'ы.** Если продукт не умеет — UI пишет «недоступно», а не имитирует успех.
8. **Один управляемый продукт на роутер.** Обнаружены оба → ошибка, изменений нет.
9. **Отказ безопаснее догадки.** Неизвестная опция/команда/версия → отказ с кодом, не «попробуем».

### 2.1. Сервер

* **HTTP API + Web panel** — единый процесс.
* **Домен**: пользователи, роутеры, шаблоны, задания, мониторинг, диагностика, аудит.
* **Планировщик**: выдаёт задания мониторинга с шагом 60 с и детерминированным jitter, не более одного задания на роутер одновременно.
* **Воркеры**: берут задания из БД (`SELECT … FOR UPDATE SKIP LOCKED`), создают команды агенту, ждут результат, проверяют, пишут события.
* **Agent gateway**: аутентификация агента, long-poll, приём результатов и отчётов, лимиты размера, идемпотентность.
* **PostgreSQL** — единственное состояние. Redis не требуется (см. §12).

### 2.2. Агент (роутер)

* **Язык**: ucode (уже зависимость продукта) + `/bin/sh` только для init-скрипта. HTTP — `curl`. Конфиг — `uci`. Никаких Python/Node.
* **Размер**: ориентир ≤ 300 КБ + снапшоты.
* **Сервис**: procd, `respawn`, запуск после сети.
* **Локальный allowlist операций** — не расширяется сервером.
* **Локальный манифест** (`manifest.json`): версия, поддерживаемые операции, whitelist UCI-опций, hard-exclude, коды ошибок, формат отчётов. Сервер валидирует шаблоны против манифеста роутера.
* **Идемпотентность**: журнал `command_id` (последние 500, с TTL 7 дней) — повторная доставка не применяет изменение дважды.

## 3. Поток применения шаблона (happy path)

```text
1. Пользователь: выбрать роутер(ы) + шаблон → «Проверить»
2. Сервер: job diff(router)  ──poll──▶ агент
3. Агент: read_state (allowlist) → JSON управляемых опций
4. Сервер: three-way diff (current / desired / last_applied)
           → add / change / delete + предупреждения (GAP, конфликты)
5. Пользователь: видит точный diff, подтверждает (для >1 роутера — по каждому)
6. Сервер: job apply(router, diff_hash, snapshot_required=true)
7. Агент: snapshot → apply_uci (валидация каждой операции) → uci commit
8. Агент: reload → дождаться завершения (service_action_status)
9. Агент: verify (get_status, get_ui_state, check_proxy, health)
10. Успех → applied_state; иначе → restore snapshot → reload → verify
11. Сервер: результат, аудит, обновление drift-статуса
```

Инварианты:

* `diff_hash` фиксирует подтверждённый набор; если состояние изменилось между diff и apply → `stale_diff`, требуется повторное подтверждение.
* Apply всегда с `snapshot_required=true`; отключить нельзя даже суперадмину.
* Удаления (`delete`) показываются отдельной группой и требуют отдельного чекбокса.
* Секретные опции не участвуют в diff в принципе (их нет в `read_state`).
* Если у роутера `product_conflict`, `unsupported_platform`, `offline`, `busy` — apply не создаётся.

## 4. Протокол «сервер ↔ агент» (кратко)

Полная спецификация: `docs/architecture/API.md`.

* Транспорт: HTTPS 1.1/2, TLS ≥ 1.2, системный CA bundle роутера.
* Модель: **long-poll** (`POST /agent/v1/poll`, hold ≤ 25 c). Пуш не нужен: пока агент держит запрос, сервер отвечает сразу при появлении команды.
* Аутентификация: per-router bearer token (256 бит, base64url), хранится на сервере как SHA-256; `X-RC-Nonce` + `X-RC-Timestamp` (окно ±300 с, nonce-кэш 10 мин).
* Идемпотентность: `command_id` (UUIDv7), `attempt`; результат — `POST /agent/v1/result`.
* Отчёты: `PUT /agent/v1/reports/{report_id}` (gzip, ≤ 2 МБ), только masked.
* Backoff: 5 с → 5 мин, jitter ±20 %, при 401 — стоп и `re_bind_required` (не долбить сервер).
* Версионирование: `agent_version`, `manifest_version`; сервер не отправляет команды, которых нет в манифесте.

## 5. Мониторинг

* Тик планировщика 10 с; для каждого роутера `next_due = last_finished + 60 с ± jitter(0…15 с)`.
* Жёсткая сериализация: один in-flight на роутер (lease в БД + локальная блокировка агента).
* База: `get_ui_state` (дешёво) + `get_status`.
* Прокси: `clash_api get_proxy_latency` для активного узла/группы (не `check_proxy` каждый цикл).
* Prokop: `get_health_status` раз в цикл (дешёвый, локальный).
* Классификация:
  * `router_offline` — 3 подряд неуспешных poll'а (≈3 мин);
  * `service_down` — роутер отвечает, `running=0` и не `stopped_by_user`;
  * `proxy_unhealthy` — delay не измерен / `check_proxy` != 0;
  * `proxy_degraded` — delay выше порога или часть тегов мертва;
  * `unknown` — нет данных (агент старый, GAP).
* Хранение: не более 30 дней — сырые точки 30 дней, часовые агрегаты 30 дней, суточные в v1 не используются (см. `DECISIONS.md` D-10).

## 6. Диагностика

* **Quick** — 8–10 команд, ≤ 120 с, доступна пользователю.
* **Full** — + логи, `check_environment`/`get_health_status` (Prokop), inbound-проверки (Forkop), `global_check masked`, ≤ 300 с.
* Групповой запуск: задание на каждый роутер, общий `batch_id`; частичный успех — норма.
* Отчёт: `state` на каждую проверку + `not_available(product)` + `not_checked(reason)`.
* Хранение: только masked, ≤ 2 МБ, TTL 30 дней, `sha256`; в UI — просмотр и скачивание.
* `support_report` не собирается (unmasked).

## 7. Версии sing-box

* Каталог: Prokop `core_releases` (официальный GitHub-релиз `shtorm-7/sing-box-extended`, только stable, только с SHA-256); Forkop — GAP.
* Установка: `component_action_async sing_box install_version <tag>` (Prokop, только extended) либо `install_stable|install_tiny|install_extended|install_extended_compressed`.
* Права: superadmin — любой роутер и staged rollout; user — только свои роутеры, только тег `extended` из каталога, 1 установка на роутер в 24 ч, с подтверждением и снапшотом.
* Предпроверки: архитектура, свободное место/память, текущий вариант, конфликт с pin, подтверждение суперадмина.
* Post-check: `show_sing_box_version` = ожидаемая, `get_status.running=1`, `check_proxy` = 0, `get_system_info.sing_box_binary_signature` изменилась.
* Staged rollout: стадии `canary (1) → 10 % → 50 % → 100 %`, ручное подтверждение между стадиями, авто-пауза при ≥ 2 неудачах подряд, окно наблюдения 24 ч.
* Rollback: переустановка предыдущей версии тем же механизмом (Prokop) + снапшот конфигурации; для Forkop — только смена варианта, не версии.
* «Официальные источники» = upstream-источник продукта; мы не добавляем свои зеркала и не подменяем URL.

## 8. Безопасность (кратко)

Полная модель: `docs/architecture/SECURITY.md`.

* Пароли — Argon2id; сессии — opaque, хэш в БД, HttpOnly/Secure/SameSite=Lax.
* 2FA TOTP (RFC 6238), политика по умолчанию `all` — обязательна для всех; допустимы `all|admins`, значения `off` нет; первый superadmin подтверждает TOTP при первом входе.
* Инвайты и binding-токены: 32 символа CSPRNG (base32, 160 бит), в БД только SHA-256, TTL 5 мин, одноразовые, атомарное погашение, rate limit.
* RBAC: `superadmin` (всё, секреты, лимиты, политика 2FA, каталог версий и rollout, аудит) и `user` (свои роутеры/шаблоны/соединения; установка sing-box на свои роутеры).
* Изоляция: все запросы фильтруются по `owner_id`; наружу — только opaque ID; чужие объекты → 404 (не 403), чтобы не раскрывать существование.
* Секреты в покое: AES-256-GCM, ключ из env/файла вне БД; TOTP-секреты шифруются; токены — только хэши.
* Агент: allowlist операций, `env -i`, argv без shell, отказ от неизвестных опций, запрет raw-вывода секретов.
* Аудит: кто/что/когда/результат, без значений секретов; append-only.
* Ограничения частоты: логин, погашение инвайта, poll, создание заданий.

## 9. Отказоустойчивость

| Сбой | Поведение |
|---|---|
| Сервер перезагрузился | Задания в БД; lease истёк → воркер подхватывает; `command_id` защищает от дублей |
| Агент перезагрузился | Журнал command_id на flash; незавершённое задание → `lost` → reconcile-задание |
| Роутер offline | Задания с истёкшим TTL не выполняются; мониторинг копит пропуски; статус `offline` |
| Reload вернул `queued` | Ждать завершения через `service_action_status` + повторная верификация; при таймауте — `needs_attention` |
| Reload упал | Restore снапшота, reload, verify; если restore невозможен — `rollback_failed`, ручное вмешательство |
| Обновление sing-box не подняло сервис | `needs_attention`, автоповтор запрещён, откат версии по кнопке |
| Обнаружены оба продукта | `product_conflict`, все mutate блокируются, read-only разрешён |
| Продукт заменён (Forkop→Prokop) | `product_changed`, applied-состояние инвалидируется, нужен новый снапшот |
| Конфиг изменён извне | Drift-детект при следующем diff; apply требует нового подтверждения |

## 10. Стек (рекомендация)

| Слой | Реализация | Почему |
|---|---|---|
| Сервер | **Node.js 24 LTS + TypeScript**, один процесс (Fastify 5) | один рантайм и один язык с фронтендом, без Redis; 100–150 МБ RSS на 100 роутеров |
| БД | **PostgreSQL 16** | jsonb для diff/отчётов, `SKIP LOCKED` как очередь, партиционирование метрик |
| Очередь | **таблица `jobs` в PostgreSQL** | состояние переживает рестарт без Redis; меньше компонентов |
| Миграции | Drizzle ORM + SQL-миграции | детерминированный деплой, явный SQL для `SKIP LOCKED` |
| Web | **React 19 + TypeScript (Vite)**, собирается в артефакт | diff-вьюер, графики, таблицы; без CDN |
| API | REST + OpenAPI 3.1 (Fastify + Zod) | генерация клиента, контрактные тесты |
| Агент | ucode + curl + procd | уже на роутере, без новых зависимостей |
| Наблюдаемость | pino (JSON) + Prometheus `/metrics` | без внешних SaaS |
| Деплой | Docker Compose (app + postgres + Caddy) или systemd | оба варианта документируются |

**Принято в интервью 2026-10-27:** Node.js 24 LTS + TypeScript (самый лёгкий из не-Go вариантов), PostgreSQL 16, очередь в БД, React SPA. **Отклонённые альтернативы:** Go 1.23+ (не выбран пользователем), Python 3.12 + FastAPI + arq (второй рантайм), Node + BullMQ + Redis (лишний брокер). Решение — `DECISIONS.md` D-01/D-02.

## 12. Почему без Redis

Требование — «состояние заданий переживает рестарт». Это даёт БД, а не брокер. Очередь на `jobs` с `SKIP LOCKED`:

* атомарный захват задания;
* leases и восстановление после падения воркера;
* прозрачная история и метрики;
* нет второй системы, которую надо бэкапить и мониторить.

Redis понадобится только при >~2000 заданий/мин, чего в v1 нет.

## 13. Этапы и критерии приёмки

| Этап | Содержание | Критерий готовности |
|---|---|---|
| 0 | Аудит | `INTEGRATION_MAP.md` согласован |
| 1 | Каркас: репозиторий, CI, миграции, health сервера, Docker | `docker compose up` → `/healthz` 200 (реализовано; см. `docs/runbooks/phase-1.md`) |

| 4 | Задания: очередь, lease, retry, timeout, reconcile | kill -9 воркера → задание подхвачено, дублей нет |
| 5 | Read state + diff + шаблоны | diff add/change/delete на фикстурах Forkop и Prokop |
| 6 | Apply + snapshot + verify + rollback | применение на тестовом роутере, откат при битом конфиге |

Каждый этап заканчивается: код + миграции + тесты + `docs/runbooks/<этап>.md` с инструкцией «как запустить и как проверить».

# Roadmap: перенос панели и создание секции при установке

Статус: **проверено на живом стенде 24.11.2026**, панель A возвращена в работу,
временная панель B удалена. Документ фиксирует результаты теста и очередь работ.

Стенд:

* панель A — `root@192.168.2.1`, `/opt/routx`, образ `ghcr.io/seriec163/routx:sha-376a933`,
  схема 33, агент 1.5.52;
* панель B — временный инстанс на том же хосте, `/opt/routxb`, порт `172.17.0.1:3001`,
  БД `127.0.0.1:5433`, `RC_PUBLIC_URL=https://routx.duckdns.org`,
  `RC_PACKAGE_SYNC=false`;
* переключение трафика — через upstream Caddy, домен и URL не менялись.

Тестировались только чтение состояния и `diff`. `apply` на реальных роутерах не
запускался, поэтому устройства не изменялись.

## 2. Найденные проблемы

### P0-1. На чистой установке секция не создаётся, а `create_sections` не срабатывает

Сценарий воспроизведён на B с эмулятором агента: создан роутер, выпущен binding-token,
выполнен `bind`, затем `probe` без секций (как сразу после установки).

Факты:

* шаблон с явной секцией и `create_sections=["autotest"]` на чистом роутере падает:
  `Секция «autotest» … не существует на роутере, и нет секции с подключением,
  к которой её можно привязать`;
* в БД ошибка сохраняется как `internal_error`, задача уходит в ретраи (3 попытки),
  в UI нет кода `section_without_connection`;
* preset-шаблон (`ForFriends`, без имён секций) на том же роутере отрабатывает:
  план `add section.rc_main.*`, `create_sections=["rc_main"]`, `default_section=rc_main`.

Причина: `mapTemplateSections()` (`server/src/domain/uci.ts:586-607`) бросает
`section_without_connection` до того, как `creatableSections()`
(`server/src/domain/uci.ts:399-405`) успевает добавить секцию в план.
То есть заявленная в документации логика «секция с `action` создаётся» на чистой
установке недостижима.

### P0-2. `probe` не заполняет `sections` и не выбирает `managed_section`

После `bind` + `probe`:

* `router_state.managed` записан, `router_state.sections` — пусто;
* `routers.managed_section` остаётся `''`, даже если в `managed` уже есть
  `section.rc_main.action=connection`;
* `sections` появляются только после ручного `POST /api/v1/routers/:id/refresh`
  (`server/src/routers/routes.ts:580`), который запускает `read_state`;
* после `read_state` с секцией `managed_section` корректно становится `rc_main`.

Причина: `probe` обновляет `router_state` напрямую и не вызывает
`resolveManagedSection()`; `sections` в ответ `read_state` формирует только агент.

Итог: свежеустановленный роутер выглядит «без секций» до ручного обновления,
хотя секция на устройстве уже есть.

### P0-3. Ошибки валидации превращаются в `internal_error` и ретраятся

`badRequest()`/`HttpError` из обработчиков не являются `JobFailure`, поэтому
`server/src/jobs/worker.ts:158-162` заворачивает их в
`new JobFailure('internal_error', …)`, а `internal_error` входит в `RETRYABLE`
(`worker.ts:29`). Следствие: понятная ошибка становится «внутренней», задача
повторяется, агент получает лишние команды, в UI нет actionable-кода.

### P0-4. Файлы `/app/data` не переносятся: зеркало пакетов ломается

После импорта в B:

* `package_mirror`: 44 строки, `119 040 872` байта метаданных;
* фактический `/app/data` в B — `2.7 MB`;
* запрос `/downloads/github-api/repos/…/releases/latest` → `500`,
  в логе `ENOENT … /app/data/packages/forkop/…/release.json`;
* на A тот же запрос отдаёт `200` и `337 216` байт.

Причина: `.rcbackup` содержит только дамп БД, мастер-ключ и манифест
(`docs/runbooks/deploy-and-migrate.md:20-32`); каталог данных (зеркало, ранее
загруженные файлы) не входит в файл переноса. Кроме того, при `RC_PACKAGE_SYNC=true`
новый инстанс начнёт качать зеркало при старте ещё до импорта, а после импорта
получит строки, указывающие на отсутствующие файлы.

Итог: после реального переезда установка/обновление через зеркало отдаёт 500.
Фолбэка на GitHub в `getReleaseJson()`/`readPackageContent()` нет.

### P0-5. Правка `Caddyfile` может молча не примениться (bind-mount на старый inode)

На хосте `/opt/routx/Caddyfile` указывает на новый inode, а контейнер
`routx-caddy-1` видел старый файл от 2 ноября:

* host inode `824845`, container inode `822524`;
* `sed -i` заменяет файл (новый inode), bind-mount остаётся на старом;
* `caddy reload` пишет `config is unchanged`, трафик продолжает идти на A;
* помог только `docker restart routx-caddy-1`.

Это не гипотетический риск: до теста Caddy уже работал с устаревшей копией
конфигурации, то есть правки конфига после 2 ноября не применялись.

### P0-6. Старый инстанс и новый одновременно исполняют одни и те же задачи

После импорта B получил копию очереди A. B сразу начал исполнять импортированные
`monitor`-задачи и отправил на Офисный роутер pending-команду из копии
`agent_commands`. Параллельно A ждал ответы агентов, которые уже ушли на B:
за 7 минут окна — 11 `monitor` → `timeout` на A.

Для `monitor` это шум, но для `apply`/`wifi_*`/`agent_update` это риск двойного
изменения конфигурации. В процедуре переезда нет шага «остановить воркер A».

### P1-7. Парольная фраза в API передаётся в base64, это нигде не описано

`passphraseFrom()` (`server/src/deploy/routes.ts:38-52`) декодирует
`x-rc-passphrase` из base64. При передаче открытым текстом возвращается
`bundle_passphrase` («неверная фраза или файл повреждён»), что уводит в сторону:
файл и фраза корректны, ошибка в кодировании заголовка.

### P1-8. Сессии переносятся без предупреждения

Экспорт содержит таблицу `sessions`, поэтому все активные входы (17 штук)
продолжают работать на новом инстансе. Это удобно, но после переезда нет
кнопки «завершить все сессии», а в документации нет предупреждения.

### P1-9. Зеркало не архитектурно-зависимо и грузится целиком в память

`ARCH='aarch64_cortex-a53'` зашит, `fetchBuffer()` читает файл целиком
(до ~87 МБ), отдача — буфером. На смешанном парке (NanoPI и др.) зеркало
бесполезно, а на слабом роутере — риск по RAM.

### P1-10. Нет проверки целостности переноса

Импорт проверяет схему и подпись, но не проверяет, что все файлы, на которые
ссылается БД, существуют; нет smoke-теста «зеркало/агент/задача/секция» после
перезапуска. Ошибки всплывают позже и как `500`.

## 3. Roadmap

### Спринт 0 — «Секция создаётся, ошибки понятны» (2–3 дня)

Статус: **сделано в ветке `routx-2.0`**.

* 0.1 — `mapTemplateSections()` больше не падает на чистой установке: секции
  с `action` создаются, в `diff` появляются `add section.<name>.action/enabled`,
  в результате — предупреждение «Будут созданы: …». При существующей секции
  поведение прежнее (reuse + warning).
* 0.2 — `probe` заполняет `router_state.sections` из `managed` (если полного
  `read_state` ещё не было) и синхронизирует `routers.managed_section`; после
  `bind` автоматически ставится `refresh_state`; `/routers/:id/state` отдаёт
  `sections`.
* 0.3 — `HttpError` сохраняет код и не ретраится; повторяются только
  `agent_timeout`, `agent_unavailable`, `db_error`.

Тесты: `server/test/routing-plan.test.ts` (чистая установка, несколько секций,
`managed → sections`), `server/test/job-failure.test.ts` (коды и ретраи).

**0.1. Создавать секцию на чистой установке.**

* `mapTemplateSections()`: если секция есть в `creatableSections(payload)`,
  не бросать `section_without_connection`, а оставить её для создания в плане;
* при `sections.length === 0` и пустом `managed` разрешать создание секции
  из шаблона (пустой `action/enabled` + ресурсы);
* в `diff` явно показывать `create_section: <name>` отдельной строкой.

Acceptance:

* на чистом роутере `diff` шаблона с `create_sections=["autotest"]` → success,
  в плане `add section.autotest.action`, `section.autotest.enabled`;
* preset-шаблон по-прежнему материализуется в `rc_main`;
* на роутере с существующей секцией поведение не меняется (reuse + warning).

**0.2. Заполнять состояние сразу после установки.**

* в обработчике `probe` (`server/src/agent/routes.ts:1013-1069`) вызывать
  `resolveManagedSection()` и сохранять `sections` (или ставить
  `refresh_state` в очередь, если `sections` пуст и `managed` не пуст);
* после `bind` автоматически запускать `refresh_state` один раз;
* `GET /api/v1/routers/:id/state` отдавать `sections`.

Acceptance:

* `bind` → `probe` с секцией в `managed` → `managed_section` заполнен без ручного refresh;
* `sections` в БД непустые после первого probe;
* в UI нет состояния «секций нет», если агент их прислал.

**0.3. Не терять коды ошибок.**

* в `worker.ts` различать `HttpError`/`badRequest` (4xx) и `JobFailure`;
  сохранять исходный код, не ретраить;
* `RETRYABLE` оставить только для `agent_timeout`, `agent_unavailable`, `db_error`;
* в UI показывать код и подсказку.

Acceptance:

* `section_without_connection` виден в `jobs.error_code` и в UI;
* задача не повторяется;
* существующие тесты очереди проходят.

### Спринт 1 — «Перенос без сюрпризов» (1–1.5 недели)

Статус: **сделано в ветке `routx-2.0`**, кроме упаковки самих файлов `rc_data`.

* 1.1 — импорт удаляет записи `package_mirror` без файлов; отсутствующие
  release/asset/raw отдаются с GitHub вместо `500`.
* 1.2 — в runbook добавлены проверки Caddy; отдельного скрипта пока нет.
* 1.3 — `RC_JOBS_PAUSED=true` останавливает воркер и планировщик целиком.
* 1.4 — сессии документированы, отзыв через существующий
  `POST /api/v1/users/{id}/revoke-sessions`.
* 1.5 — `passphrase_encoding` + тест + пример `curl`.
* 1.6 — `GET /api/v1/deploy/verify`; подключение к UI импорта — следующий шаг.

**1.1. Переносить данные зеркала или пересобирать его после импорта.**

Вариант A (предпочтительный): включить в `.rcbackup` манифест файлов `/app/data`
(размер, sha256) и либо упаковывать их, либо после импорта помечать зеркало
`missing` и пересобирать в фоне.
Вариант B: после импорта очищать `package_mirror` и запускать sync.

Дополнительно:

* `getReleaseJson()`/`readPackageContent()`: при `ENOENT` — fetch-through на GitHub
  и понятный статус, а не `500`;
* `RC_PACKAGE_SYNC` по умолчанию `false` для импортированного инстанса, пока
  зеркало не проверено;
* в `/api/v1/packages` показывать «файлов нет на диске».

Acceptance:

* после импорта `/downloads/github-api/...` отдаёт `200`;
* `package_mirror` и диск согласованы;
* при отсутствии файла — `502 mirror_unavailable`, не `500`.

**1.2. Безопасная процедура переключения Caddy.**

* в runbook: не использовать `sed -i` для bind-mounted файла; писать через
  `cat > file` или перезапускать контейнер;
* после `caddy reload` проверять, что контейнер видит новый файл
  (`docker exec routx-caddy-1 grep reverse_proxy /etc/caddy/Caddyfile`);
* проверять, что `/healthz` отвечает именно новым инстансом (build/uptime);
* добавить `caddy validate --config`.

Acceptance:

* в runbook есть проверка «reload применился»;
* повторный прогон теста переключения не требует ручной диагностики.

**1.3. Не исполнять задачи дважды.**

* шаг «остановить воркер A» (env/флаг или `docker compose stop app` с сохранением
  Caddy) до импорта;
* либо колонка `instance_id` в `jobs` и условие в `claimJob`;
* при импорте отменять `running/queued` задачи, которые не являются read-only,
  и показывать их список.

Acceptance:

* во время переключения ни один `apply` не исполняется дважды;
* в логах нет чужих pending-команд, выданных новым инстансом.

**1.4. Документировать и обезопасить перенос сессий.**

* в runbook: сессии переносятся, это ожидаемо;
* после импорта — кнопка «завершить все сессии» и запись в аудит;
* в UI импорта — предупреждение.

**1.5. Исправить документацию по API импорта.**

* указать, что `x-rc-passphrase` — base64;
* при ошибке декодирования возвращать `passphrase_encoding`, а не
  `bundle_passphrase`;
* пример `curl` в runbook.

**1.6. Проверка целостности после импорта.**

* smoke-скрипт: `/healthz`, `/readyz`, вход, список роутеров, `read_state` одного
  роутера, `diff` preset-шаблона, скачивание файла зеркала;
* результат показывать в UI импорта.

### Спринт 2 — «Агенты и задачи не клинят» (1–1.5 недели)

Статус: **сделано в ветке `routx-2.0`**, кроме пункта 1 (ucode самообновления).

* 1 — панель больше не считает обновление успешным сразу: `agent_update`
  ждёт смену `agent_version` (или совпадение с версией из образа) до 2 минут
  и падает с `agent_update_not_applied`; Wi-Fi-обновление ждёт до 90 секунд.
  Осталась доработка самого `jn_self_update.uc` (таймауты apk, откат, лог
  stderr) — нужен живой роутер.
* 2 — проверка возможностей: перед Wi-Fi-командой панель сверяет
  `agent_version` с минимальной (`server/src/agent/features.ts`), старый агент
  получает `agent_outdated`, а Wi-Fi-обработчик сам обновляет его и повторяет.
* 3 — `RC_WORKER_CONCURRENCY` (по умолчанию 2), блокировка строки роутера при
  захвате, `AbortController` по таймауту и проверка сигнала в `waitForCommand`.
* 4 — после рестарта read-only задачи возвращаются в очередь, изменяющие
  остаются `timeout` + `needs_attention`.
* 5 — Wi-Fi-пароль шифруется в `jobs.payload` (`key_enc`), аргументы
  `wifi_*`/`apply_connections`/`manage_connection` — в `agent_commands.args`
  (`__rc_sealed`); расшифровка только при выдаче агенту.
* 6 — `waiting_for_router` в API и UI, TTL `RC_QUEUED_JOB_TTL_DAYS` (7 дней),
  событие `queue_expired`.

Осталось: доработка `jn_self_update.uc` (таймауты apk, откат при неудаче,
подробный лог) — требует проверки на живом роутере.

Закрывает ранее найденные эксплуатационные проблемы:

1. **Самообновление агента**: таймауты/`--wait` для `apk`, проверка версии после
   рестарта, откат, ожидание фактической смены версии в `agent_update`.
2. **Capability handshake**: агент присылает список операций, панель проверяет
   перед постановкой задачи, автоматически обновляет агент или объясняет
   «нужна версия X».
3. **Конкурентный воркер**: N воркеров, отдельный приоритет для `monitor`,
   `AbortSignal` в обработчики и `runCommand`, реальная отмена по таймауту.
4. **Восстановление прерванных задач**: фазы/чекпоинты; read-only задачи
   переставлять в очередь, изменяющие — `needs_attention` с кнопкой «Повторить».
5. **Секреты в очереди**: шифровать payload задач и `agent_commands`, чистить
   после ack, тест «в дампе нет Wi-Fi/VPN-секретов».
6. **Офлайн-задачи**: статус `waiting_for_router`, TTL, уведомление, массовая отмена.

### Спринт 3 — «Интерфейс и наблюдаемость» (1 неделя)

1. Ленивая загрузка страниц, `ErrorBoundary`, разбиение `RouterDetail.tsx`.
2. `AbortController` и защита от гонок в `useApi`, visibility-aware polling,
   SSE для задач/уведомлений.
3. `/metrics` (prom-client): очередь, длительность задач, ошибки по типам,
   offline-роутеры, ошибки обновления агента, размер БД/диска.
4. Лимиты контейнеров и настройка Postgres под роутер.

### Спринт 4 — «Чтобы не вернулось» (1 неделя, параллельно)

1. Превратить эмулятор агента из этого теста в интеграционный тест:
   `bind → probe → refresh → diff → apply` на Postgres.
2. E2E (Playwright): вход, создание роутера, секции, Wi-Fi, обновление.
3. Общий контракт API (OpenAPI/сгенерированные типы) вместо ручного
   `web/src/lib/types.ts`.
4. Линтер/форматтер в CI, разбиение `jobs/handlers.ts` и `routers/routes.ts`.
5. Архитектурно-зависимое ленивое зеркало с потоковой отдачей.

## 4. Чек-лист приёмки переезда (повторять на каждом стенде)

1. `POST /deploy/inspect`: `compatible=true`, `same_domain=true`.
2. Импорт: `202`, перезапуск, `/readyz` зелёный, схема совпадает.
3. `deploy/status`: отпечаток мастер-ключа равен источнику, счётчики совпадают.
4. Вход существующей сессией по тому же домену.
5. Список роутеров: все онлайн, `agent_version` тот же.
6. Офисный роутер: `managed_section`, `sections`, подключения на месте.
7. `refresh_state` и `diff` preset-шаблона проходят без ошибок.
8. Скачивание файла зеркала — `200`.
9. Переключение обратно: агенты вернулись, задачи идут.
10. Остановить второй инстанс, удалить тома, отозвать временные сессии.

## 5. Порядок и оценка

| Приоритет | Работа | Оценка |
| --- | --- | --- |
| P0 | Создание секции на чистой установке + probe/refresh + коды ошибок | 2–3 дня |
| P0 | Зеркало: перенос/пересборка, fetch-through, статус | 3–4 дня |
| P0 | Процедура Caddy и «один воркер» при переезде | 1–2 дня |
| P1 | Документация импорта, сессии, smoke-тест | 1–2 дня |
| P1 | Самообновление агента, capability handshake | 4–5 дней |
| P1 | Конкурентный воркер, отмена, восстановление задач | 4–5 дней |
| P1 | Секреты в задачах/командах | 2–3 дня |
| P2 | Фронтенд (lazy, гонки, ErrorBoundary) | 4–5 дней |

Если делать только три вещи: **0.1**, **0.3**, **1.1**. Они закрывают ровно те
сценарии, которые сломались в тесте: «поставили RoutX — секции нет», «ошибка
непонятна», «после переезда не работает зеркало».
